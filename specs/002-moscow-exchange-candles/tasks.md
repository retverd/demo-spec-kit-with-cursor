## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: Не имеет зависимостей — можно начинать сразу
- **Foundational (Phase 2)**: Зависит от Phase 1 (документы и базовые решения должны быть зафиксированы) — БЛОКИРУЕТ все пользовательские истории
- **User Stories (Phase 3+)**: Обе истории зависят от завершения Phase 2  
  - User Story 1 (P1) может начинаться после завершения Foundational (Phase 2)  
  - User Story 2 (P2) зависит от User Story 1 (переиспользует `CandleRecord` и `MoexClient`)
- **Integration (Phase 5)**: Зависит от завершения реализаций US1 и US2
- **Polish (Phase 6)**: Зависит от завершения всех желаемых пользовательских историй и интеграционных тестов

### User Story Dependencies

- **User Story 1 (P1)**: Может быть реализована сразу после Foundational (Phase 2); не зависит от других историй
- **User Story 2 (P2)**: Зависит от User Story 1 (нужны рабочие `CandleRecord`, `MoexClient` и валидация свечей), но должна оставаться независимо тестируемой (можно мокать клиент)

### Внутри каждой пользовательской истории

- Тесты (если включены) должны быть написаны и падать до реализации кода
- Модели (`src/models/`) создаются до сервисов (`src/services/`)
- Сервисы реализуются до CLI и интеграционного слоя (`src/cli/main.py`, `tests/integration/`)
- Основная реализация должна быть завершена до интеграционных тестов
- История считается завершённой до начала следующей по приоритету (кроме явно помеченных параллельных задач [P])

### Параллельные возможности

- Все задачи, помеченные [P], могут выполняться параллельно, если соблюдается отсутствие зависимостей и конфликтов по файлам
- В Phase 1–2 можно параллельно вести документацию (`research.md`, `data-model.md`, `quickstart.md`, контракты) и обновление зависимостей
- В рамках US1 можно параллельно писать юнит‑тесты для `MoexClient` и реализовывать модель `CandleRecord`
- В рамках US2 можно параллельно писать юнит‑тесты и реализацию `XLSXWriter`, пока CLI‑слой реализуется последовательно
- Интеграционные тесты Phase 5 могут писаться параллельно между собой после готовности сервисов и CLI
- В Phase 6 можно параллельно заниматься документацией, рефакторингом, проверкой логирования и прогоном тестов

## Implementation Strategy

### MVP First (User Story 1 Only)

1. Завершить Phase 1: Setup (исследование API и базовая документация)
2. Завершить Phase 2: Foundational (контракты, валидация свечей, зависимости) — **КРИТИЧЕСКИЙ блокирующий этап**
3. Завершить Phase 3: User Story 1 (полностью рабочий `MoexClient` + тесты)
4. **ОСТАНОВИТЬСЯ И ПРОВЕРИТЬ**: Протестировать User Story 1 независимо (моки HTTP, проверка получения свечей за 7 дней)
5. Пригодно к демонстрации, если достаточно только извлечения данных без XLSX

### Incremental Delivery

1. Setup + Foundational → фундамент готов (контракты, валидация, зависимости)
2. Добавить User Story 1 → протестировать независимо → при необходимости задеплоить/продемонстрировать как минимум функционал извлечения данных
3. Добавить User Story 2 → протестировать независимо (файл XLSX и его структура) → задеплоить/продемонстрировать полный сценарий LQDT/TQTF→XLSX
4. Добавить интеграционные тесты (Phase 5) → убедиться, что end‑to‑end сценарий стабилен
5. Выполнить этап Polish (Phase 6) → привести документацию, логи и код в состояние, пригодное для долгосрочной поддержки

### Parallel Team Strategy

При наличии нескольких разработчиков:

1. Совместно завершить Phase 1–2 (исследование и контракты, базовая валидация)
2. После завершения Foundational:
   - Разработчик A: User Story 1 (`CandleRecord`, `MoexClient`, юнит‑тесты клиента)
   - Разработчик B: User Story 2 (тесты и реализация `XLSXWriter`)
3. После завершения User Story 1:
   - Разработчик A: интеграционные тесты в `tests/integration/test_end_to_end.py`
   - Разработчик B: CLI‑интеграция `moex-lqdt` и доработка документации (`quickstart.md`, README)
4. Оба разработчика совместно завершают Phase 6 (рефакторинг, типы, логи, финальный прогон тестов)
